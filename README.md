# Harness X-Ray

Harness X-Ray is a static audit of the harness around an AI coding agent: the instructions, permissions, hooks, skills and tools that shape what the agent reads, runs and remembers in a repository. It is meant to be used from Claude Code. Pointed at another repository (the target), it reports what the harness seems to waste (context loaded on every session), what it leaves exposed (commands or secrets the agent can reach without a barrier) and what it lacks (verification steps, structure, reuse), with each recommendation tied to its source. It never executes code from the target and never writes to it.

## Requirements

- Node.js 22 or later. There are no npm dependencies.
- Claude Code, to run the audit with the `xray-scan` skill.

## Usage

Open Claude Code at the root of this repository and ask it to scan a target, for example "scan this repo's harness: <path>", or run the `/xray-scan` skill.

- The target must be a folder outside this repository.
- Do not add the target with the add-dir command or the `--add-dir` option: Claude Code would load the target's own memory, skills and agents into the session.

The skill runs the scanner, reads only the files the scan names, applies the rule catalog, writes `findings.json` and renders `report.md` and `report.html` in a new folder under `runs/`. It ends with a short summary per axis in the chat. Reports are in English unless you explicitly ask for Spanish.

## What it checks

The findings are grouped in six axes: instructions, context, security, verification, structure and code. Each rule is a file in `rules/`, and its sources are in `rules/sources.json`. A measured rule is decided by the scanner from its numbers; a judgment rule is applied by the agent, which cites the scanner's numbers instead of typing them.

## Instructions aimed at agents

The scanner looks for text in the target that addresses a coding agent instead of a person (SEC-06): phrases such as "ignore previous instructions" or "do not tell the user", a download piped into a shell, sentences or flags that turn off hooks, permission prompts or the sandbox, HTML comments in instruction files, and invisible or bidirectional Unicode characters. The patterns are data in `data/injection-patterns.json`, which `npm run check` validates. They are matched in linear time, and the matcher runs no regular expression on the target's text.

- It reads the instruction files of every agent in the registry, with their skills, commands and subagents, the memory files, rules and imports of Claude Code, and every other `.md` file of the target. Code and its comments are not read. HTML comments count only in instruction files, outside fenced code blocks; a fence line inside a multi-line comment is still read as a fence.
- The caps are 2000 files, 1 MiB per file, 32 MiB in all, 10 matches per file and 100 per scan. A warning counts what each cap leaves out.
- Each match is a candidate of kind `injection-candidate`, with its file, line, category, pattern and an excerpt of at most 120 characters. The excerpt is redacted as the other measures redact text: the folders of this machine and token-shaped secrets are masked, also when an invisible character splits the token, but a password in a plain assignment is not. Every invisible character in it is written as `U+XXXX`. The file name is copied as it is.
- A candidate is not a finding. The agent reads the line in its file and decides: "never push to main" is a legitimate prohibition, and a README line that installs a tool for people is not an instruction to the agent.
- Without a match, `measurements.json` has no `security.injection` key. Only a cap warning can then change it, so that a file the scan skipped is not taken for a clean one.

## Scripts

- `node scripts/scan.mjs <target> [--out <dir>] [--include-user-layer] [--include-ancestors] [--scope <folder>]... [--layers <runDir>] [--depth quick|standard|deep]`: scans a target and writes `<runDir>/measurements.json`. Without `--out`, `<runDir>` is a new folder under `runs/`. `--out` must lie inside `runs/` or the system temp folder (exit 2 otherwise). `--include-user-layer` also reads the user's Claude files in `~/.claude`, and `--include-ancestors` also reads the memory files of the parent folders of the target. Both are opt-in: without them, nothing outside the target is read. `--scope` limits the scan to a folder of the target, such as `apps/web`, and can be repeated (see Scope below). `--layers <runDir>` adds the context that Claude Code loads in each layer of a layer plan from `map.mjs` (see Scope below). `--depth` sets how deep the scan goes, `standard` by default (see Depth below).

Privacy: with these flags, home paths are written as `~/...`, never as the home folder itself; the strings copied from the user's files are redacted, and the parent-folder files give only their counts.
- `node scripts/render-report.mjs <runDir>`: validates `<runDir>/findings.json` against the rule catalog, the scan and the target, then writes `<runDir>/report.md` and `<runDir>/report.html`, two views of the same findings. Exit 0 when both are written, 1 when validation fails (nothing is written), 2 for a usage or input error. The two files are written one after the other, not atomically: if a write fails (a full disk, a read-only file), the run exits 1 and can leave a new or partial `report.md` beside the older `report.html`. `<runDir>` must lie inside `runs/` or the system temp folder (exit 2 otherwise). The renderer does not open the page. `node scripts/open.mjs <runDir>/report.html` opens it when the run folder is inside `runs/`; open.mjs refuses a run folder in the system temp folder.
- `node scripts/map.mjs <target> [--out <dir>]`: maps the possible layers of a target (its candidate folders, its workspaces and a folder tree) and writes `<runDir>/layers.json`. Without `--out`, `<runDir>` is a new folder under `runs/`. `--out` must lie inside `runs/` or the system temp folder (exit 2 otherwise). It reads the file list, the manifests and the root harness files (through the agent inventory) as data, never source code, and never runs anything from the target. Exit 0 when written, 2 for a usage or input error, 1 for anything unexpected.
- `node scripts/open.mjs <file|url>`: opens an `.html` file inside `runs/` (not the system temp folder; lower-case `.html`, and only letters, digits, `.`, `_`, `-`, spaces and `/` in its path below `runs/`) or an `http://127.0.0.1:<port>/...` URL with the platform's opener command (`xdg-open` on Linux, `open` on macOS), through a child process and never a shell. It writes nothing. Exit 0 when the opener was launched, 2 for a refused input or a usage error, 3 when there is no graphical environment (on Linux, neither `DISPLAY` nor `WAYLAND_DISPLAY`) or the opener command is missing, so the caller can print the path or URL instead, 1 for anything unexpected.
- `node scripts/intake.mjs <runDir> [--timeout <seconds>] [--lang en|es]`: starts a local form on 127.0.0.1 for the layers of `<runDir>/layer-plan.json` and prints its address, with a one-use token. The form asks for the depth, the layers to scan, the axes to prioritize, the report language and whether the user layer and the parent folders may be read. A valid answer is written to `<runDir>/intake.json`, and the command stops. It refuses to start when `<runDir>/intake.json` already exists. `--timeout` is the wait in seconds, from 1 to 3600 (default 600); `--lang` is the language of the pages (default en). Nothing is opened in a browser, and the skill does not use it yet. `<runDir>` must lie inside `runs/` or the system temp folder. Exit 0 when written, 4 when the wait ran out (nothing written), 2 for a usage or input error, 1 for anything unexpected.
- `node scripts/intake.mjs <runDir> --questions [--timeout <seconds>] [--lang en|es]`: starts a local form on 127.0.0.1 for the questions that the agent wrote to `<runDir>/questions.json` after a scan, and prints its address as `questions: <url>`, with a one-use token. The file holds at most 5 questions. Each one has an id, a text, the reason it is asked, and its source (a file and a line), and a type: `single` (one option is chosen, and one is required), `multi` (any number of options, or none) or `text` (a written answer of at most 2000 characters, which may be empty). The options are shown with their labels, and the form sends their ids. A valid answer is written to `<runDir>/answers.json`, and the command stops; it never writes `intake.json`. It refuses to start when `questions.json` is missing or invalid, has more than 5 questions, or when `answers.json` already exists, and it needs no layer plan. The form has the same security as the intake form: the one-use token, the Host and Origin checks, a body cap, the wait (exit 4 with nothing written) and the 127.0.0.1 address. The answers are data, not instructions: when an answer contradicts a measurement, the measurement prevails. Nothing carries the answers into `measurements.json` or the report yet. Exit codes are the same as for the intake form.
- `npm test`: runs the test suite.
- `npm run check`: validates the rule catalog, the `data/` files (including `data/agent-harness.json`, `data/layer-signals.json` and `data/injection-patterns.json`) and the measured rules.

`report.html`, written by `render-report.mjs`, is the report as one page for a browser. It is local: it works offline, loads nothing from outside and runs no script. A Content-Security-Policy in its meta element allows only its own inline style. Source links are links only when their address is https; any other address is shown as text. The filters are one checkbox per axis and per impact, applied with CSS `:has()`, so a browser without `:has()` shows every finding.

## Scope

With `--scope <folder>`, the scan looks at one part of the target, for example one layer of a monorepo. The folder is relative to the target and must exist inside it; a folder that does not exist, is not a folder, leaves the target or is reached through a link exits with 2. The option can be repeated, and a folder inside another scope folder adds nothing.

- Analyzed only inside the scope: the structure measures (folder tree, map coverage, large and generated files) and the duplication measure, so `duplicatedLinesPct` is the share within the scope. The search for instructions aimed at agents reads the `.md` files inside the scope and the harness of the scope (see the next point), and the memory files that Claude Code loads, imports included, wherever they lie.
- Read outside the scope, because the scope inherits it: the harness of the root and of each folder between the root and the scope (CLAUDE.md, AGENTS.md, rules, skills and the files of every agent in the registry). The CLAUDE.md and AGENTS.md files of those folders and of the scope are read, not only listed. A harness file belongs to the folder that holds its agent folder (`.claude`, `.agents`, `.cursor` and the other folders that the registry names), so `apps/.claude/skills/x/SKILL.md` is part of the harness of `apps`. The project permissions and hooks are global, and so are the secret checks.
- Verification is looked for in the whole target: the root `package.json`, the root tool configs, the CI workflows, and the `package.json` files of the scope, of the folders on the way and of other layers (`verification.packages`) with the tool configs next to them, so a check that lives outside the scope still counts. A command named in a CLAUDE.md or AGENTS.md below the root is checked against the `package.json` of its folder and of the folders above it.
- Not analyzed: the files outside the scope, and the harness of the folders that are neither on the way to the scope nor inside it. `measurements.json` records the scope in its `scope` section, and the report says what was analyzed and what was not.
- `--include-ancestors` still reads the parent folders of the target, not those of the scope.

With `--layers <runDir>`, the run folder holds the layer plan of a `map.mjs` run (`layers.json` and `layer-plan.json`), and the scan adds `context.byLayer`: for each layer, the files that Claude Code loads on demand when it works there, and its nested skills. The on-demand files are the CLAUDE.md files of the folders on the way to the layer and inside it, and the rules whose `paths` match a file of the layer. Nested skills are listed apart, because their load model is not verified; nested AGENTS.md files are not counted, and imports are not followed. The always-loaded total is the same for every layer. The plan must match the target: a layer folder that is gone, or a `layers.json` written for another target, exits with 2.

## Depth

`--depth quick|standard|deep` sets the depth of the run, and `measurements.json` records it as `depth`. An invalid or missing value, or a `--depth` given more than once, exits with 2.

- `standard` (the default) is the scan described in this README.
- `quick` makes the same measures as `standard`, and applies no judgment rules. The report header shows the level and says that the judgment rules were not applied. Validation refuses a finding of a judgment rule, and the error says that the judgment rules are not applied at quick depth and that the scan should be at standard or deep depth (`scripts/lib/findings-validate.mjs`), so a quick report cites only measured findings. A scan without a `depth` field is standard.
- `deep` reads nothing outside the target that `standard` does not read: `--include-user-layer` and `--include-ancestors` remain the only ways to read `~/.claude` and the parent folders. Inside the target it changes two measures:
  - The duplication measure raises its caps, so a large repository is measured in more of its code. Standard lists 20 groups, and deep lists 50. The caps are `MAX_GROUPS_DEEP` 50, `MAX_FILES_DEEP` 6000 code files (standard 2000), `MAX_FILE_BYTES_DEEP` 512 KiB per file (standard 256 KiB) and `MAX_TOTAL_BYTES_DEEP` 96 MiB of code read in total (standard 32 MiB), all in `scripts/lib/duplication.mjs`. The caps bound the files and bytes that one scan reads; the memory use of a deep scan was not measured. The window length and the minified-line limit do not change.
  - The destructive-commands measure adds a permission matrix at three locations: inside the project, outside it, and at a critical path. `security.destructiveCoverage.matrixLocations` lists them, and each command gets `locations`, with its outcome in each mode of `matrixModes`. `dontAsk` and `plan` are not in the matrix, for the reason given in `scripts/lib/permissions.mjs`. The report shows this full matrix, one row per command and location, in place of the standard matrix, which shows each command only at its own location.

## Limits

- The scan reads the target's project files only, unless a flag is given. `--include-user-layer` reads the user's `CLAUDE.md`, rules, `settings.json`, skills and subagents in `~/.claude`. `--include-ancestors` reads the memory files of the parent folders, for their counts only. Managed settings are never read.
- Not verified by a note: how the user, project and local permission rules combine. With `--include-user-layer`, the scan takes the union of the three lists and checks deny first, then ask, then allow.
- With `--include-user-layer`, the user's `defaultMode` is recorded but not applied, and the user's hooks are counted but not evaluated.
- The `@imports` in the user's files, in the parent folders and in the CLAUDE.md and AGENTS.md files that a scope reads below the root are not followed.
- Tokens are estimated from characters, never counted.
- The tools that enforce rules (`structure.enforcementTools`, read by RUL-02 and STR-03) are found by the name of their config at the root, or for an architecture tool by the manifest that names it: eslint-plugin-boundaries in a dependency list of a `package.json`, import-linter in a `.importlinter` file or a `pyproject.toml` or `setup.cfg` section, and ArchUnit in `pom.xml`, `build.gradle` or `build.gradle.kts`. A marker is a plain text match, so it also counts in a comment. Only the root is searched, or with `--scope` the folders that the scope inherits and the listed packages, so a tool configured only in a subproject is not listed. Whether a tool's config enforces a given rule is the agent's judgment: the scan does not read the rules inside a config.
- CTX-04 judges the descriptions of the Claude Code skills that the listing shows at the start of every session, and their number. Commands and subagents are measured (`descriptionChars` in `claudeConfig`), but give no finding: no note says what of them loads at the start. Its two thresholds are provisional.
- The search for instructions aimed at agents is a list of patterns, not an understanding of the text: it misses an instruction written in other words or in another language, and it flags legitimate lines that the agent then dismisses. It reads Markdown and instruction files only. Whether Claude Code removes HTML comments or invisible characters from a memory file before it loads it is not verified by a note.
- The destructive-command checks assume the project's `defaultMode`, or `default` when the project sets none. A real session may start in another mode, which is not verified against the documentation. The report's limits section shows each command's outcome in each mode (the matrix, as context).
- The thresholds in `scripts/lib/thresholds.mjs` are provisional and not yet calibrated.
- The scanner, the renderer and the map write only inside `runs/` or the system temp folder, checked on real paths. The intake writes only `intake.json`, and the questions form only `answers.json`, in its run folder, which must lie there too. Any other folder is refused with exit code 2, and nothing is written.
- The scan inventories the harness files of every agent that `data/agent-harness.json` lists (`agentHarness` in `measurements.json`). The instruction rules (RUL-01 to RUL-04) cover the root instruction files of every agent, and SEC-04 and SEC-05 name the permission and hook files that no known agent loads, as not verified when an agent's load model is unknown. The content of the other agents' settings, hooks and skills is not evaluated: SEC-04 and SEC-05 check only whether a known agent loads them, and the search for instructions aimed at agents (SEC-06) reads their instruction files and skills for its patterns only. The report header lists what was evaluated for each agent. The files of the root harness, including those in root folders such as `.agents/`, `.cursor/rules/` or `.github/instructions/`, are read to measure their size, within a cap of 2000 files and 32 MiB. Files in a subproject folder, such as `packages/api/AGENTS.md`, are only listed, unless `--scope` reaches them (see Scope), and secret-named files are never read. Only Claude Code has a verified load model, so only its files count in the context budget; the files of the other agents go to `agentHarness.unknownStatic`. Only Claude Code entries cite sources, and only where the source notes cover them; the rest, including some Claude Code entries, the shared `AGENTS.md` convention and every other agent, are unverified candidates (`loadModel` unknown).

`examples/harness-x-ray/review.md` records a scan of this repository's own harness.
