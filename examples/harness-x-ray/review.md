# Harness X-Ray self-scan review

This review records the scan of this repository's own harness. The report itself is not versioned: it is regenerated by scanning a copy of the repository. This file says what the scan found, what remains, and why.

## How this scan was run

- The scanner refuses a target inside this repository, so the scan ran on a copy of the branch in the system temp folder. The copy was made into a git repository.
- The `xray-scan` skill ran `scripts/scan.mjs` on the copy. The agent wrote `findings.json`, and `scripts/render-report.mjs` checked it against the rule catalog, the scan and the target. The check passed on the first run. The report is in English.
- Two problems that preview scans found were fixed before this scan: the secrets test fixture versioned a dotenv file and a PEM file with fake values (SEC-03, high), and CLAUDE.md had a broken inline-code reference (RUL-04, medium). The secret files are now built in the system temp folder at test time.
- The report's own limits apply. The user layer and the parent folders of the target were not read. The scan assumed the `default` permission mode. A real session may start in another mode, which is not verified against the documentation; the report's limits section shows the SEC-02 outcome of each command in each mode (the matrix).

## Medium findings

### SEC-01 · Project permissions are broader than the defaults

**What the scan found.** Two wildcard allow entries for shell commands, and no deny or ask rule narrows them:

- `.claude/settings.json:4`: `Bash(node scripts/scan.mjs *)`
- `.claude/settings.json:5`: `Bash(node scripts/render-report.mjs *)`

Measured as `wildcard-shell-allow` at `/security/permissions/allow/0` and `/allow/1`.

**Why it stays.** The target path is an argument and changes on every run, so an exact-command entry would need one entry per target. In the scan's simulation, none of the 16 destructive commands in the scanner's list is decided by an allow rule. Each one asks under the default mode.

**Residual risk.** The wildcard still passes the scanner's `--out` option, and the renderer takes a run folder as its argument. Since v0.2 (V02-01), the scanner and the renderer refuse any folder outside `runs/` and the system temp folder, checked on real paths (`checkRunDir` in `scripts/lib/run-dir.mjs`), so they can no longer write `measurements.json` or `report.md` elsewhere without a prompt. One limit remains: the system temp folder is allowed, and other processes can write there too. The destructive list is short, so a destructive command outside it would not be measured at all.

**What would change the decision.** A new scanner or renderer option that writes outside `runs/` and the system temp folder would make the wildcard broad again, and the entry would have to be narrowed. The `--out` limit that this paragraph used to ask for is in place since v0.2 (V02-01; see open decision 1).

### SEC-05 · Security rules exist only as text

**What the scan found.** CLAUDE.md states two prohibitions:

- `CLAUDE.md:49`: "Never execute code from a target repository."
- `CLAUDE.md:50`: "Never write outside this repository, except to the system temp folders used by tests."

No deny rule covers either one (`deny` is empty in the measurements). The only PreToolUse hook judges secret file names. The impact is medium by the impact table, and that rating is an opinion.

**Why it stays.**

- The scanner does not run target content. The development rules require that target files be read only through `scripts/lib/safe-fs.mjs` and that nothing from a target be executed or imported. The hostile-injection test checks that a fixture's package.json scripts do not run and that nothing is written into the target.
- For the agent, only the scanner, the renderer and `npm test` run without a prompt. Any other command asks. No project default mode is set, so the default mode applies.
- Deny rules were not added on purpose. A project deny cannot be undone from local settings, and a broad one would block development, because the tests write to the temp folder.

**What would change the decision.** A PreToolUse hook on Bash and PowerShell that refuses commands which run a file from outside this repository, plus deny rules for the write paths that the permission syntax can express, as the rule recommends. The hook would have to allow the tests' writes to the temp folder. Setting `acceptEdits` in the project would also change the picture, because SEC-01 would become high.

## Low findings

### SEC-02 · Destructive commands pass or depend only on manual confirmation

**What the scan found.** All 16 destructive commands in the scanner's list ask under the default mode, and no command passes. A PreToolUse hook runs for each of them: its matcher is `Read|Grep|Bash|PowerShell` and its `onFailure` is `block`, so `failsOpen` is false. Measured as `hook-not-verified` at `/security/destructiveCoverage/commands/0` to `/commands/15`, one trigger of low impact per command. The evidence is `.claude/settings.json` and the hook script `scripts/hooks/guard-secret-reads.mjs`.

This row is new with V02-03. Before it, a fail-closed hook gave no SEC-02 finding, although the scan cannot tell whether the hook blocks these commands without running it.

**Why it is low.** The hook runs for these commands and fails closed, but the scan does not run it, so it cannot say whether the hook blocks `rm -rf`, `git push --force` or the other commands. The simulated outcome stays `asks` by the mode. `CLAUDE.md` describes the hook as blocking calls that name a secret file, which points to no block on these commands, but this review does not count that description as a measurement. The impact stays low whatever the reading of the script says.

**What would change the decision.** This review does not record a reading of `scripts/hooks/guard-secret-reads.mjs` for these commands. The rule asks for one: the agent reads the script and says in the finding whether it covers the commands. A deny or ask rule for each command would remove the finding (open decision 2). The fail-closed setting depends on Claude Code v2.1.295 or later, as the SEC-02 rule says.

### COD-04 · No reuse step before writing new code

No instruction file tells the agent to search for an existing helper before it writes one. CLAUDE.md names `scripts/lib/` as the shared modules, and `.claude/rules/dev.md` names two helpers, but no line says to search first. The measured duplication is 0.21% of lines across 34 files, with one 11-line block copied between `scripts/scan.mjs` and `scripts/render-report.mjs`.

The step is not added. Its text would load in every session that works on `scripts/` or `test/` files, the scope of `.claude/rules/dev.md`, so it costs tokens each time. The rule's evidence is a third-party benchmark that the rule has not verified. It stays a hypothesis for a controlled test: the same helper-writing task with and without the step, counting the new helpers that duplicate code in `scripts/lib/`. See open decision 5.

## Findings the scan does not give, and why

**SEC-03, secrets: no finding.** The scanned copy has no secret-named file and no literal secret, since both lists are empty in the measurements. A read of the `.env` file at the root has no permission rule, but the hook runs for it and fails closed. The hook judges names, not content, so a secret kept under another name passes.

**Fixture memory.** The scanner reads `claudeMdExcludes` from `.claude/settings.json` (`**/test/fixtures/**`). The self-scan lists the eleven memory files under `test/fixtures/` as not-loaded, with loadReason `claude-md-excludes` and that pattern as `excludedBy`. None of them is in the budget, in the text the rules read, or among the memory candidates, which are now two (`CLAUDE.md` and `.claude/rules/dev.md`). The memory measure does not read their content. The secrets measure still scans them for secret values, on purpose, because Claude's Read can open them. That the pattern follows gitignore-style matching is not verified by a note.

**Fixture skills.** The self-scan lists six skills under `test/fixtures/` as nested skills (`scope: nested`): five in `test/fixtures/full-config/` and `deploy-notes` in `test/fixtures/secrets/`. Not verified by a note: that nested skills load on demand (this repository's CLAUDE.md states it). They are on demand in the scan, and none counts in the budget. The `internal-helper` skill has `disable-model-invocation`, so it is not-loaded. Nested commands and subagents are not listed, because no note says they load from a subfolder.

**Injected instructions.** The hostile-injection fixture's `CLAUDE.md` contains instructions aimed at the auditor. During the self-scan, the skill did not act on them and named them only in its chat summary. No catalog rule covers injected instructions, so the report does not list them. A scanner-level test checks that the scanner runs none of the fixture's package.json scripts and writes nothing into the target.

## Open decisions

1. Whether `--out` should be limited to the runs folder, and whether the renderer's folder argument should be limited the same way (SEC-01). Decided in v0.2 (V02-01): both are limited to `runs/` and the system temp folder, in the scanner and in the renderer.
2. Whether to add deny or ask rules for the destructive commands in the scanner's list. The scan gives SEC-02 low for them (`hook-not-verified`), and a deny or ask rule for each command would remove it. This is a choice and not a fix the rule requires (SEC-02).
3. Whether to build the hook and deny rules that SEC-05 recommends, given that the tests write to the temp folder (SEC-05).
4. Decided in v0.2 (V02-02): the scanner reads `claudeMdExcludes` and inventories the nested skills, so the inventory shows the fixtures as excluded or nested. Pending verifications, none stated by a note in `rules/sources.json`: the pattern syntax of `claudeMdExcludes` and the settings files that accept it; whether it covers `.claude/rules/`; whether nested skills load on demand; and whether Claude Code loads an import of an excluded file. Also not verified by a note: whether AGENTS.md is covered by `claudeMdExcludes`; case-sensitive matching; a trailing slash dropped (gitignore's directory-only meaning is not kept); ancestors not checked against the patterns; and whether Claude Code reads a root AGENTS.md when the only root CLAUDE.md is excluded (the scan reports that case as undeterminable, not as a finding). Until they are verified, the scanner's figures for these cases are assumptions.
5. Whether to add the reuse step to `.claude/rules/dev.md`, after the controlled test (COD-04).
6. Whether to add a catalog rule for instructions aimed at the auditor.
